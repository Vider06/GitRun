## 2.1 GSR authorization pipeline — audit progress (OPEN)

This section tracks the original v1.5.0 GSR authorization phase, not the separate numbered GitDockRun mount checklist above. It is not closed until current-head CI and the remaining trust-boundary evidence below are recorded.

### Fixes applied on `refactor/v1.5.0-total-cleanup`

- `gitrun-scheduler/src/api_service.rs`: Unix API socket handling caps active request handlers at 64, rejects excess connections without spawning a thread, and releases each capacity permit through RAII. The request reader enforces an absolute 10-second deadline across all reads (not merely a per-read inactivity timeout), caps a request line at 1 MiB, and requires the JSONL newline terminator. Responses also have a 10-second socket write-inactivity timeout. Regression tests cover capacity/release, newline framing and a byte-trickling peer. This does not replace timeouts on separate outbound/network operations.
- `gitrun-core/src/settings.rs` and `gitrun-gsr/src/api_gate.rs`: `RegisterPolicy.allowed_entries` is now enforced before an authorized operation is produced. An entry must match an exact allowlist value; `*` is an explicit catch-all, and an empty list denies registration. Backend path validation remains an independent check.
- `gitrun-gsr/src/api_gate.rs`: `GitDockRun CONNECT` and `DISCONNECT` are denied at the gate unless the requested job exactly matches the caller's verified current job. Backend checks remain as defense in depth.
- `gitrun-core/src/api_policy.rs`, `gitrun-gsr/src/api_gate.rs` and `gitrun-scheduler/src/api_service.rs`: `GitRegisterRun.permanent` now uses the same canonical boolean parser in request validation, GSR and backend; only lowercase `true` and `false` are accepted. Mixed-case or alternate spellings fail closed instead of authorizing one effect and executing another.
- Regression tests cover capacity release, register-entry deny-by-default/exact/wildcard behavior, GSR rejection of an unlisted entry, connect/disconnect current-job matching, and canonical `permanent` boolean acceptance/rejection.
- `gitrun-scheduler/src/api_service.rs`: the shared `execute_gsr_authorized_stream` path re-checks invocation repository/workflow/run/job/runner claims against `VerifiedCaller`, authorizes through GSR, verifies the authenticated internal handoff, and only then accepts and dispatches to `ExecutionBackend`. A recording-backend test proves exact-operation dispatch and denial-before-backend; five mismatched caller claims fail closed. Pure validators cover runner/repository binding, run ID, container labels, active-job decisions, GitHub job status/runner/conclusion and workflow claims. Unix-stream integration tests run the production handler with an injected identity provider for accepted status requests, unmanaged peers, runner claim mismatch, missing run ID, inactive jobs, active-job fallback success/mismatch, workflow-claim mismatch and GitHub lookup failure; rejected cases must not emit `Accepted`. The real Docker cgroup/PID-reuse resolver still needs its own focused test harness.

### Protections confirmed in the current source trace

- Linux peer PID comes from `SO_PEERCRED`; the host resolves the PID's cgroup to a Docker container, re-reads the cgroup after Docker inspection to guard against PID reuse, and requires the managed-runner label.
- Runner and repository claims are compared to container metadata. The invocation must include a run ID; container-bound job/run labels must match when present. The authoritative GitHub job must name the same runner and be `in_progress`; the workflow run is fetched from GitHub before `VerifiedCaller` is constructed.
- GSR checks the closed API/operation pairing, argument schema, effective repository policy, resource policy and command policy (for docked execute) before creating `AuthorizedOperation`.
- The backend revalidates sensitive resource bindings and immutable Docker container identity. The HMAC envelope covers the serialized operation, timestamp and nonce.
- Important boundary qualification: `ExecutionAuthority` currently signs and verifies inside the same process and returns the operation to the local backend. This integrity round-trip is not a separate-process security boundary. Closure must document the intended trust model and prove the exact authorized operation reaches the handler unchanged; do not claim process isolation that is not implemented.

### Remaining work before this original phase can close

1. **Real peer/container resolver verification:** the production socket handler now has injected-provider integration tests for success and key fail-closed branches. Still test the concrete Linux `SO_PEERCRED` PID → `/proc` cgroup → Docker-inspect resolver, especially cgroup reread/PID reuse, unmanaged peers and Docker metadata/inspect failures. These tests must prove no backend dispatch occurs on identity-resolution failure.
2. **Argument and policy matrix:** the full `GitRunApi × GitRunOperation` support matrix and a minimal valid-arguments case for every supported pair are now tested. Still enumerate each operation's missing-required, optional, unknown-argument, resource-scope and policy allow/deny cases.
3. **Protocol and streaming residuals:** frame-size, malformed/truncated JSONL, nonce-length, timestamp-expiry, timestamp-tampering, replay and payload-MAC tests now exist. Add request-ID correlation and disconnect/partial-stream semantics; retain the fact that HMAC is an in-process round-trip, not a process boundary.
4. **Evidence on final HEAD:** rerun full GitRun CI and security analysis after this set of changes. Record the exact final SHA and results, and rerun any privileged/runtime check whose source coverage is claimed.

No confirmed bypass was established by this pass for the above remaining items; they are required coverage and contract-consistency work, not findings of equal severity. Mark this phase closed only after items 1–4 are tested or explicitly accepted with a documented scope.
