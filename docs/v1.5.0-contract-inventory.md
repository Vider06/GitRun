### Internal dependency edges observed from manifests

- `gitrun-core` is the shared base and has no path dependency on another GitRun crate.
- `gitrun-exe` depends on `gitrun-core`.
- `gitrun-gsr` depends on `gitrun-core` and `gitrun-exe`; its API gate performs authorization, not execution.
- `gitrun-scheduler` depends on core, exe, GSR, Vault and updater.
- `gitrun-setup` depends on core and updater.
- `gitrun-recovery` depends on core, scheduler, updater and setup.
- `gitrun-dashboard-tauri` depends on core, scheduler, Vault, GSR and setup.
- `gitrun-cli` composes scheduler, core, GSR, setup, updater, recovery and dashboard.

The broad composition edges are consistent with the separation between policy, authorization, orchestration, operator UX and privileged effects. This inventory has not yet proven that all public types or runtime call paths respect those intended boundaries; that is a follow-up audit task.

## 2.1 GSR authorization pipeline — audit progress (OPEN)

This section tracks the original v1.5.0 GSR authorization phase, not the separate numbered GitDockRun mount checklist above. It is not closed until current-head CI and the remaining trust-boundary evidence below are recorded.

### Fixes applied on `refactor/v1.5.0-total-cleanup`

- `gitrun-scheduler/src/api_service.rs`: Unix API socket handling now applies 10-second read/write deadlines before starting a worker, caps active request handlers at 64, rejects excess connections without spawning a thread, and releases each capacity permit through RAII. A unit test covers the cap and permit release. This bounds slow-client thread exhaustion; it does not replace timeouts on any separate outbound/network operation.
- `gitrun-core/src/settings.rs` and `gitrun-gsr/src/api_gate.rs`: `RegisterPolicy.allowed_entries` is now enforced before an authorized operation is produced. An entry must match an exact allowlist value; `*` is an explicit catch-all, and an empty list denies registration. Backend path validation remains an independent check.
- `gitrun-gsr/src/api_gate.rs`: `GitDockRun CONNECT` and `DISCONNECT` are denied at the gate unless the requested job exactly matches the caller's verified current job. Backend checks remain as defense in depth.
- Regression tests cover capacity release, register-entry deny-by-default/exact/wildcard behavior, GSR rejection of an unlisted entry, and connect/disconnect current-job matching (both denial and permitted cases).

### Protections confirmed in the current source trace

- Linux peer PID comes from `SO_PEERCRED`; the host resolves the PID's cgroup to a Docker container, re-reads the cgroup after Docker inspection to guard against PID reuse, and requires the managed-runner label.
- Runner and repository claims are compared to container metadata. The invocation must include a run ID; container-bound job/run labels must match when present. The authoritative GitHub job must name the same runner and be `in_progress`; the workflow run is fetched from GitHub before `VerifiedCaller` is constructed.
- GSR checks the closed API/operation pairing, argument schema, effective repository policy, resource policy and command policy (for docked execute) before creating `AuthorizedOperation`.
- The backend revalidates sensitive resource bindings and immutable Docker container identity. The HMAC envelope covers the serialized operation, timestamp and nonce.
- Important boundary qualification: `ExecutionAuthority` currently signs and verifies inside the same process and returns the operation to the local backend. This integrity round-trip is not a separate-process security boundary. Closure must document the intended trust model and prove the exact authorized operation reaches the handler unchanged; do not claim process isolation that is not implemented.

### Remaining work before this original phase can close

1. **Transport-to-authorization regression tests:** exercise peer/container identity rejection, runner and repository mismatch, absent/mismatched run ID and job, inactive/completed GitHub jobs, workflow mismatch, and unlisted resources. Prove every rejection occurs before the backend can perform a side effect. Extract a pure validator or inject Docker/GitHub lookups if needed to make these tests deterministic.
2. **Complete API contract matrix:** enumerate every `GitRunApi × GitRunOperation` pairing, required/optional/unknown arguments, resource scopes, policy denial, and both allowed and denied paths. Existing tests are examples, not yet a complete matrix.
3. **Protocol/framing tests:** add explicit expiry-boundary and malformed-nonce tests; cover invalid, oversized, partial and EOF-terminated JSONL frames. `handle_stream` currently reads one line but does not explicitly require the newline terminator, so a complete JSON object followed by EOF may still parse. Decide and enforce the intended framing contract.
4. **Authorized-vs-executed semantics:** `GitRegisterRun` policy parses `permanent` case-insensitively, while the backend currently interprets only the exact string `true` as permanent. Align both sides with one strict or normalized parser and test mixed-case input, so the effect cannot diverge from the authorization interpretation.
5. **Evidence on final HEAD:** run the full GitRun CI and security analysis after these fixes. The Rustfmt bot generated a formatting-only commit after the initial code commits; any `action_required`/unexecuted workflow is not a pass. Record the exact final SHA and results, and rerun any privileged/runtime check whose source coverage is claimed.

No confirmed bypass was established by this pass for the above remaining items; they are required coverage and contract-consistency work, not findings of equal severity. Mark this phase closed only after items 1–5 are tested or explicitly accepted with a documented scope.

## 3. Cross-crate trust-boundary checklist

These are the required traces; the checklist is not complete until each has a code reference and at least one positive, negative and failure/recovery test.

- [ ] Workflow environment + CLI arguments → API invocation and canonical argument parser.
- [ ] Runner/peer identity → authenticated socket request → verified caller → authoritative GitHub run/job → effective API/resource policy → authorized operation.
- [ ] Authorized operation → executor protocol authentication/replay handling → concrete handler → Docker/host/Vault side effect → result/event stream.
- [ ] Desired runner state + GitHub/Docker snapshot → pure reconciliation plan → external Docker/GitHub mutation → persisted observation/retry.
- [ ] Settings/config editor snapshot → validation → persistence → other processes re-read the same state; specify concurrency protocol.
- [ ] Vault scope selection → master-key resolution → AES-GCM decrypt → caller authorization → secret delivery and audit event.
- [ ] Update manifest/signature/hash → downloaded artifact/archive validation → backup → filesystem replacement → health/startup validation → rollback.
- [ ] Startup/recovery report → repairable issue selection → repair action → postcondition check → durable healthy/failure state.
