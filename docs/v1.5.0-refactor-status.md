Last reviewed: 2026-10-11

This file is the durable progress tracker for the seven-point v1.5.0 plan. “Done” means the named change exists in this branch; it does not certify every related subsystem or security property.

## 1. UI performance and polish — PARTIAL

### Completed in this PR
- Removed the misleading static “UI READY” status and made the version footer report loading, a real version, or an unavailable state.
- Made the sidebar reversible and persistent; improved active navigation and accessibility metadata.
- Centralized common layout/error styling and removed unnecessary static inline styling from the audited views.
- Logs no longer fetch the system journal when the Security Events tab is opened; they load the journal on demand.
- Overview reuses its original telemetry promise after the fast first paint instead of starting a second batch of telemetry requests.
- The dashboard requests only the latest bounded event window; the event reader seeks from the end of the JSONL file.
- Overview's critical-event count streams the JSONL file instead of materializing its full contents.

### Still missing
- A reproducible before/after baseline for startup time, navigation latency, idle CPU, peak memory, log rendering and bundle/package size.
- Manual end-to-end UI verification on the actual Tauri desktop runtime and representative large event histories.
- A retention/rotation plan for the append-only event file. The new dashboard read path bounds memory for recent logs, but an exact recent-critical count still scans the durable file and the file itself can grow indefinitely.

## 2. Expected-vs-actual behavior contracts — NOT COMPLETE

### Completed
- Added regression tests for reading the newest events in file order, zero limit, and a JSONL file without a trailing newline.
- The dashboard save path compares submitted config/settings snapshots with current values and rejects a stale screen instead of silently accepting an obviously stale save.

### Still missing
- A crate-by-crate contract inventory: responsibilities, inputs, outputs, invariants, side effects, limits, timeouts, failure modes and recovery semantics.
- A requirements-to-code-to-test matrix and explicit evidence for each contract.
- Tests for stale-save rejection and repeated successful saves in the same UI session. The snapshot comparison narrows lost-update cases, but because check and write are not one cross-process atomic transaction, it is not a complete cross-process compare-and-swap guarantee.

## 3. Code consistency and missing enforcement — PARTIAL

### Completed
- The repository UI no longer presents legacy mount settings as an enforced mount allowlist.
- The security screen and settings types now explicitly identify the existing mount-policy fields as legacy/stored-only; they remain deserializable to avoid breaking existing settings files.
- The repository screen explains that repository-level API overrides cannot re-enable globally disabled capabilities.
- Global Logic Containers rules now explain their immediate, separate persistence behavior.
- The existing direct-Docker-socket opt-in confirmation and backend validation remain in place.

### Still missing / blocked
- **A real mount feature is not implemented.** The closed GitDockRun API has no `Mount` operation, no executor handler and no runtime enforcement for MountPolicy/mountable. The UI intentionally no longer offers controls that imply otherwise.
- Docker's documented bind-mount flow supplies mounts at container creation (`docker run --mount`). A live mount API would require a separately designed privileged Linux namespace mechanism, strict source/destination validation, read-only and recursive-mount enforcement, a persistent mount lease/registry, reliable cleanup on disconnect/container exit, and integration/negative tests. This is not safe to approximate with `docker exec` or an unreviewed `nsenter` command.
- Recommended safe next step: choose and document the feature contract before implementation — (a) only mounts declared before runner creation, (b) a separately reviewed Linux-only runtime namespace feature, or (c) remove the legacy schema in a deliberate migration. Until then, mount policy stays fail-closed by not exposing a mount operation.
- The broader audit for other settings that are declared but not consumed, swallowed errors, duplicated implementations and incomplete validation remains open.

## 4. Scaling and core lifecycle — PARTIAL

### Completed
- Runner/activity/host telemetry use existing backend caches.
- Logs avoid eager journal I/O and avoid reading the complete event queue just to render the latest events.
- Overview's delayed refresh reuses completed work.

### Still missing
- Audit queue/worker pressure, cancellation, limits, retries, idempotency and recovery across scheduler/GSR/executor lifecycles.
- Benchmark many repositories/runners, very large event histories, slow GitHub API calls and repeated navigation/refresh.
- Define event storage retention/rotation and measure end-to-end scaling, not just dashboard memory use.

## 5. Component and trust-boundary flow mapping — PARTIAL

### Completed
- Traced the reviewed GitDockRun path through CLI argument parsing, GSR API/operation/resource policy, authenticated executor handoff, ApiExecutionBackend, DockRegistry binding and immutable container ID checks.
- Confirmed that Read/Write/Execute/Melt validate repository/resource policy and that execution additionally requires GSR command policy.

### Still missing

- Verify the effective policy at the final side-effect boundary for all paths, including all remote/VM backends.

## 6. Security review and exploit testing — PARTIAL

### Completed
- Existing CI security regression gate and CodeQL ran green on the previously verified branch head.
- The reviewed UI/backend code does not claim the stored mount configuration is active enforcement.
- Regression tests were added for the new event queue reader/count behavior.

### Still missing

- Add executable negative tests for allow/deny precedence, canonical paths/symlinks/traversal, recursive submounts, read-only behavior, stale/missing container binding, cleanup after disconnect and crash/restart **after the mount architecture is approved**.
- Add race tests around concurrent settings writers and review atomicity across the dashboard and other processes.
- Continue adversarial review of identity binding, path/command handling, race windows and recovery/fallback paths across the full repository.
