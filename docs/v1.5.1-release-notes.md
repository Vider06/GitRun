# GitRun 1.5.1 — recovery and documentation notes

**Target source version:** 1.5.1  
**Baseline:** GitRun 1.5.0, including the recovery/runtime migration merged by PR [#103](https://github.com/Vider06/GitRun/pull/103) on 2026-10-20.

This document describes the source changes proposed for 1.5.1. A merged pull request or a `version.txt` value is not, by itself, evidence that a signed release artifact has been published; check [GitHub Releases](https://github.com/Vider06/GitRun/releases) for published artifacts.

## Recovery of legacy 1.5.0 installations

The 1.5.0 installation may have a runtime directory and configuration created by the desktop user even though the scheduler and GSR services run with a protected service identity. This can make root-owned, mode-`0600` health and crash records unreadable to an unprivileged dashboard and can cause GitDockRun registry ownership checks to reject reconciliation.

The recovery path now distinguishes **protected state** from damaged state. An unprivileged process cannot read the root-only setup marker, health record or crash record; that permission denial is not, on its own, evidence that setup is incomplete or that the record is corrupt.

The privileged repair path is intentionally narrow:

- It validates the trusted `/etc/gitrun` and systemd directories, the environment file, file types, hard-link counts, ownership and permissions before applying changes.
- Automatic legacy migration is limited to the canonical `/var/lib/gitrun` state directory and the known desktop-user-owned configuration/settings files. Noncanonical state paths and unexpected owners fail closed.
- It repairs the state-directory entry and validated configuration/settings files only. It does **not** recursively `chown` the state tree, loosen protected health/crash-record permissions, or delete Vault data, backups, update data or state records.
- It reinstalls the packaged `gitrun.service` and `gitrun-gsr.service` contracts, reloads systemd, and enables/restarts both services. Local edits that differ from the packaged service contract are not silently accepted as equivalent hardening.

For an affected installation, use GitRun's Repair service path from the installed recovery UI/CLI after installing a build that contains these changes. Do not work around an ownership error with a recursive `chown -R` or by making protected records world-readable. Inspect and preserve unexpected state, and validate the repair on the actual host before considering migration complete.

## Kitty / Smart Scheduler retention

The Workflow Model distinguishes short-lived high-resolution samples from compact long-term summaries:

- The raw five-minute observation window is bounded to 2,016 buckets (seven days).
- Older history is retained as aggregates rather than as an ever-growing sequence of raw observations.
- Four-week blocks become compact logical months; twelve such months (48 weeks) become a compact logical year. Yearly and lifetime summaries keep long-term workload shape available without retaining every original sample.
- Model, forecast, occurrence, and decision-audit collections remain individually bounded. Missing/incomplete job-start coverage is not interpreted as proof that no job started.

The compact month/year are fixed-duration aggregation tiers, not calendar-month accounting. Forecast-quality scores remain heuristic readiness measures rather than calibrated probabilities. Kitty is optional and disabled by default; predictive warm-pool changes require separate opt-in, sufficient fresh history, acceptable evaluated forecast quality and available capacity, and remain subordinate to deterministic reconciliation, GSR authorization and resource-pressure backpressure.

## Versioning

The product/source version is maintained in the root `version.txt` and the shipped dashboard metadata. Individual Cargo crates use independent SemVer versions; their crate versions are not expected to equal the product version.

| Component | Version for this change | Reason |
|---|---:|---|
| GitRun product/source | `1.5.1` | Root source version and shipped dashboard metadata |
| `gitrun-setup` | `0.9.1` | Guarded legacy runtime-permission migration |
| `gitrun-recovery` | `0.6.4` | Protected-state diagnostics and repair orchestration |
| GitRun Recovery Tauri bundle | `0.4.1` | Recovery UI package metadata |

The root Cargo lockfile must keep its local package records consistent with the changed Cargo manifests. The dashboard npm lockfile must keep its package-root version aligned with `package.json`. Registry dependency versions are not bumped merely because the GitRun product release changes.

## Verification and deployment boundaries

Automated tests can validate path/ownership guards, protected-state classification, systemd contract matching and the ordinary scheduler regression suite. They do not replace testing the repair workflow on the target host: confirm the service account, unit contents, runtime directory ownership, GSR watchdog liveness and a successful scheduler reconciliation after repair. Verify the exact checks attached to the relevant pull request and test the published artifact before deploying it.

The security model and residual limitations remain documented in [SECURITY.md](../SECURITY.md), [the security model](SECURITY_MODEL.md), and the [1.5.0 contract inventory](v1.5.0-contract-inventory.md). The latter is a historical audit snapshot, not a substitute for the 1.5.1-specific notes above.
